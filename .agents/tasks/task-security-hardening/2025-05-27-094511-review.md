# Security hardening for AiValidMarket

A broad sweep adding rate limiting, API key authentication, prompt injection mitigations, input sanitization, concurrency controls, CORS restriction, security headers, Docker non-root execution, and frontend XSS prevention. The approach adds a middleware/sanitizer layer without restructuring existing routes, making it low-risk from a regression standpoint but leaving several gaps that reduce the effective security posture.

**Watch for:** Semaphore leak on `executor.submit` failure (confirmed). Timing-vulnerable API key comparison (confirmed). Unauthenticated status/result endpoints that expose full validation output (confirmed). Chat endpoint passes unsanitized `message` directly into LLM prompt without the same delimiter treatment applied to `idea_text` (confirmed).

## High-level view

The concurrency model wraps the old bare-thread approach in a `ThreadPoolExecutor` gated by a semaphore, but the semaphore is acquired before `executor.submit` and only released inside the submitted function. If the pool is saturated and `submit` raises, the semaphore count is permanently decremented.

API key authentication is applied to mutation and search endpoints but not to `GET /status/<task_id>` or `GET /result/<task_id>`, which return the full validation output including the original idea text. Any client who observes a task UUID can read results without authenticating.

Prompt injection mitigation is inconsistent: `idea_text` gets backtick delimiters in the LLM prompts and `sanitize_input` stripping before processing, but the chat endpoint's `message` field is never sanitized and is concatenated directly into the system-level context string with no delimiter.

The API key check uses Python's `!=` string comparison, which is subject to timing side-channel attacks. For a bearer-token check, `hmac.compare_digest` is the standard constant-time alternative.

The Docker hardening correctly drops to a non-root user and uses gunicorn, but the image installs Node.js solely for the frontend build step and leaves it in the final image, inflating attack surface. A multi-stage build would fix this and also resolve the `curl` dependency question in the HEALTHCHECK.

## Semaphore lifecycle in validation.py

The semaphore is acquired in the request handler and released in the `finally` block of `_run_validation`. If `executor.submit(_run_validation, ...)` raises — which happens when the pool is shut down or at resource limits — the semaphore permit is consumed but never returned:

```python
if not _validation_semaphore.acquire(blocking=False):
    return jsonify({"error": "Too many concurrent validations"}), 429

task = task_manager.create_task()
executor.submit(_run_validation, task.id, idea_text)  # <-- can raise
```

The fix is a try/except around `submit` that releases the semaphore on failure:

```python
try:
    executor.submit(_run_validation, task.id, idea_text)
except Exception:
    _validation_semaphore.release()
    return jsonify({"error": "Service unavailable"}), 503
```

Without this, under sustained load the semaphore can silently drain to zero and the endpoint returns 429 permanently until the process restarts.

## API key comparison timing

In `middleware/security.py`:

```python
if api_key != Config.API_KEY:
    return jsonify({"error": "Invalid or missing API key"}), 401
```

Python's `!=` on strings short-circuits on the first differing byte, leaking key length and prefix via response timing. Replace with `hmac.compare_digest(api_key, Config.API_KEY)` which runs in constant time regardless of where the strings differ.

## Authentication gap on status and result endpoints

`GET /api/validation/status/<task_id>` and `GET /api/validation/result/<task_id>` do not carry `@require_api_key`. The result payload includes the full idea text, analysis, and report. Any logged or leaked task ID gives unauthenticated access to the complete validation output. If the API key is intended to gate all sensitive data access, these endpoints should also require it.

## Chat message prompt injection surface

The `chat` endpoint validates `chat_history` roles (preventing system-role injection from history), but the current user `message` is appended to the messages list without any sanitization or delimiter:

```python
message = data["message"]  # no sanitize_input, no delimiter wrapping
```

Meanwhile `idea_text` in both `idea_analyzer.py` and `report_generator.py` is wrapped in triple backticks with explicit instructions to treat it as data. The chat `message` gets no such treatment. At minimum, apply `sanitize_input` and consider delimiter wrapping in the system prompt's instructions.

## Docker image structure

Node.js and npm are installed to build the frontend but remain in the runtime image. A multi-stage approach — build frontend in one stage, copy the built assets into a slim final stage — would remove ~200MB of unnecessary toolchain from the production image and reduce the attack surface. The HEALTHCHECK uses `curl`, which is currently installed but would be lost in a multi-stage refactor; a Python-based alternative (`python -c "import urllib.request; urllib.request.urlopen('http://localhost:5001/health')"`) would be more resilient.

## Rate limiter per-worker state

The limiter is configured with `storage_uri="memory://"`, which stores counters in-process. Gunicorn with `--workers 2` forks two processes, each with independent counters. A client can effectively make 2x the configured rate limit (120/min instead of 60/min). For single-node deployments, `redis://` would provide shared state.

## Log sanitization truncation

The logger's `_sanitize` wrapper applies `sanitize_log_input(msg, max_length=2000)` to all messages. Callers constructing error messages longer than 2000 characters (e.g., large stack traces passed via f-string) will be silently truncated. This could mask diagnostic information in production error scenarios where the interesting detail is near the end of a long message.
